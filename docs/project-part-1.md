# Submission

Your submission should be a link to your team's Github repository for the project.

## Assessment

Each team member should have contributions visible in the repository because that is how you will be assessed. In particular, the quality of the plan in terms of the README and Issues will affect all team members, and evidence must be provided on Github that you agree with these plans.

If the team plans it all offline, and one student uploads everything (not recommended), the rest of the team is still responsible for registering their approval via a thumb or comments.

## Outcomes

The completion of this portion of the project requires the following components

- A Github repository for your project,
- A **README** in the repository describing the desired outcome of the project and how a user should run the project (this can be aspirational for now). Additional useful information may be included in the **README** as the team desires. It can have a file extension, but I will not prescribe what you use (I typically use **README.md**, but you should feel free to use what you prefer).
- Open Issues in the Github repository describing the tasks that the team will complete to produce the project described in the **README**.

## Process

I recommend the following process to get the team coordinated around these outcomes. This is not required if the team has a different process they agree to follow. If you follow a different process, please keep in mind that the grading rubric will still be applied, so there must be evidence of your contributions to the project both in terms of generating contributions and critiquing contributions.

1. Assign one team member to be the Tech leader. They should create the repo in Github under their account. Additional tooling can be setup too.
2. Other team members should fork the repo under their accounts.
3. All team members should agree on how to communicate about updates to the main repo (email, Canvas, text, Github, etc.). Notification settings on Github can be a useful tool for this, but do not assume your teammates receive the same notifications as you unless you have all agreed and confirmed to communicate this way.
4. Assign one team member to be the Communication leader. They should create or update the README in a branch in their repo to describe the agreed plan. When it is ready, they should open a Pull Request (PR) to merge the updated README into the main repo.
5. Assign remaining team members as Design leader(s). They should open the issues in the main repo describing the tasks the team needs to complete the project.
6. All team members should review the README PR to determine whether it fairly describes what they agreed. Updates should be made to the PR until everyone on the team approves. Then the PR should be merged.
7. All team members should read the open issues created by the Design leader(s). The issues are a useful place to revise and discuss the scope of each task. From that discussion, new tasks may need to be created in new issues or revise other issues.

## Delegated Tasks

I recommend the following division of duties for this part with some tips about the skills involved, but your group may divide them differently.

Note that these roles do not carry over to the following weeks with the important exception that the Tech leader will own main GitHub repository, which will make them a gatekeeper for acceptance of the other members' contributions. (Git is fundamentally agnostic about the which repository is the main one, so it could be changed later if need be. In the interest of avoiding a deep dive on git and GitHub, it would be good if the Tech leader can commit to playing that role throughout the course.)

#### Tech leader

- Initialize the project structure, start a github repository, and share it with the team.
- Availability to complete this first step in a timely manner to allow the other team members to complete their parts.
- Git, GitHub, and/or Python tooling experience would be valuable to provide the team with a good starting repo.

#### Communication leader

- Create a git branch on your fork.
- Add or update the README describing the analysis or application the group discussed.

- Open a pull request to merge your README into the Tech leader's repo.
- Provide clear explanation of the analysis or application.

#### Design leader(s)

- Open issues on the Tech leader's repository for the tasks that the team will need to complete the project.
- Breakdown the full project into pieces of work that can be delegated.
- Provide clear descriptions of the tasks required.

## Non-delegated Tasks

Every team member will be assessed on

- the clarity of the README to describe the goal of the project and
- the clarity of how completing the Issues will lead to the goal in the README

If the README or Issues for your team are not clear, then there should be discussion on the README PR or the Issues trying to resolve how the team will make them more clear.
